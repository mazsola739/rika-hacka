Maze Escape Solver

An optimal solver for Code In – Way Out: Hack the Maze, an online hackathon by Deutsche Telekom IT Solutions. It plans the fewest steps, trap triggers and district rotations from the start to the exit of a 17×17 maze.

    The challenge hands every entry a maze as an XML string and expects a list of actions back. The test engine replays those actions, and the maze counts as solved only if the player ends on the exit. The solver is a small command-line program:
    
        
    
          
    inputMaze XML from the command line
    
          →
          
    xml2json.tsParse start, exit, walls and traps
    
          →
          
    pathfinder.tsBuild the model, run the A* search
    
          →
          
    json2xml.tsWrite the Actions XML to stdout
    
        
    
        
    The test engine starts it as node dist/solution.js "<Maze>…</Maze>", waits up to 60 seconds, and reads the answer from standard output. Anything else printed there would break the XML, so the program prints nothing but the answer.
    
        
    The goal is the fewest actions. Every step and every rotation counts as one, so a half turn of a district costs two.
    
      
    
    
    

    
    
      
    
        
    Rules
    
        
    The rules below are what the challenge's test engine actually enforces. Every solution on this page was checked against that engine.
    
        
    The board
    
        
      
          
    • The maze is 17×17 cells, rows and columns numbered 1–17. The outer ring is wall.
      • 
          
    • The start and the exit sit on the outer ring, never in a corner.
      • 
          
    • Walls and traps can only be placed inside, in rows and columns 2–16.
      •

    • A step must end inside the maze (rows and columns 2–16) or exactly on the exit, and it cannot cross a wall.
      • 
          
    • Because a step is at most 14 cells, crossing the whole maze from the start to the exit always takes at least two steps.
      • 
        
    
        
    Levels
    
        
    
          
    LevelAddsEffect
    
          
            
    1WallsPlain maze.
    
            
    2TrapsTouching a trap sends the player back to the start, and the trap disappears for good.
    
            
    3RotationThe inside is split into nine 5×5 districts. A district can be turned left or right, and its walls and traps turn with it. The district the player stands in cannot be turned.
    
              
        
    
        
        
    A quirk of the engine: its path check only works for steps to the right or down. For steps to the left or up it only checks the cell where the step ends, so such a step could jump over a wall. The solver never relies on this. Every step it plans is legal in every direction, and it only ever touches a trap by ending a step exactly on it.
    
      
    
    
    

    
    
      
    
        
    How the solver works
    
        
    1. Parsing
    
        
    xml2json.ts reads the start, the exit, the walls and the traps with regular expressions over the whole string. It does not care whether the XML arrives on one line, with Windows line endings, or with spaces around the numbers. The first version parsed line by line and broke on anything but one tag per line.
    
        
    2. The model
    
        
      
          
    • Cells are numbered 0–288 (row × 17 + column). Each inner cell knows its district (0–8) and its position inside that district (0–24).
      • 
          
    • For every district and each of its four orientations, a lookup table says which wall or trap sits in which cell. A cell is checked with a single array read, whatever the district's orientation.
      • 
          
    • Orientations that look identical (a symmetric district, or an empty one) are merged, so the search never rotates a district pointlessly.
      • 
        
    
        
    3. Rotate only when it matters
    
        
    Rotations of different districts don't interfere with each other, and a rotation doesn't affect anything until the player walks through that district. So any solution can be reordered without getting longer: each rotation moves to just before the step that first passes through or lands in its district. The search uses this. It never tries rotations on their own; instead, every step can be preceded by the rotations it needs:
    
        
      
          
    • A district the step only passes through is rotated only if its current orientation blocks the way.
      • 
          
    • The district where the step ends may be put into any orientation, because the player will be stuck with that orientation while standing in it.
      • 
          
    • The player's own district can never be rotated.
      • 
        
    
        
    This removes most of the branching. Without it, a search from the start could rotate nine districts in any combination before taking a single step.
    
        
    4. The reduced maze
    
        
    Any district except the player's own can be rotated at any time. So whether a cell can be reached depends only on three things: the cell, the orientation of the player's own district, and which traps are gone. That is 289 × 4 = 1,156 states per set of removed traps, against 289 × 49 ≈ 75.8 million for the full board. The reduced maze is used twice:
    
        
      
          
    • Exact solvability check. Removing a trap never makes anything unreachable: the only thing a trap does is send the player back to the start, which is reachable anyway. So the solver keeps removing every reachable trap until the exit appears or nothing changes. Unsolvable level-3 mazes used to burn 25 seconds; now they are rejected in a few milliseconds.
      • 
          
    • Search estimate. A breadth-first search backwards from the exit gives, for every reduced state, the number of steps needed if rotations were free and traps could be crossed. It never overestimates, and it never drops by more than the cost of an action. That makes it a consistent A* heuristic, so the search stays optimal.
      • 
        
    
        
    5. A* search
    
        
      
          
    • A state is the cell, the orientation of all nine districts (2 bits each) and the set of removed traps (one bit each), packed into a single number.
      • 
          
    • Moves are generated cell by cell along each of the four directions, up to 14 cells. A wall stops the line. A trap ends it: the step may land on the trap, which sends the player to the start and removes the trap. The exit ends it too.
      • 
          
    • The cost of a move is one for the step plus the rotations that precede it. Costs are small integers, so the open list is a bucket queue.
      • 
          
    • The search stops when the exit is taken off the queue. With a consistent heuristic, that path has the fewest actions.
      • 
          
    • Safety net: the exact search stops after 3 million states or 25 seconds. A weighted search then finds a valid but possibly longer answer. In testing the net was never needed; the slowest maze took 195 ms.
      • 
        
    
        
    6. Back to actions
    
        
    The path is a list of states. Between two neighbouring states, every district whose orientation changed becomes one or two Rotate actions, using the cheaper direction. The movement becomes one Step. When a trap was triggered, the step's target is the trap, not the start where the player ended up. json2xml.ts prints the result.
    
      
    
    
    

    
    
      
    
        
    Verification
    
        
    Two independent checks were run on every maze.
    
        
      
          
    • The official engine. A small harness loads the challenge's own test engine and lets it replay each answer. It joins the program's output lines without separators, exactly as the real tester does. A maze counts only if the engine reports it solved.
      • 
          
    • A brute-force reference. A separate breadth-first search, written from scratch and using a literal copy of the engine's rotation loop, finds the true minimum number of actions. It is slow, so it gives up on large level-3 searches; those mazes are checked by the engine only.

    • Random mazes have 15–50% walls, up to four traps, and a random start and exit. Every second one is written on a single line.
      • 
          
    • "Unsolvable" means there is no way out at all. The exact check proved it for every maze in that column; the reference confirmed it wherever it finished.
      • 
          
    • Wherever the reference finished, the solver's action count matched the true minimum exactly.
      • 
          
    • The example mazes were checked by hand as well: the solver lands on a trap on purpose in level 2 to remove it, which opens a shorter route.
      • 
          
    • Edge cases: a step longer than 14 cells, an exit right next to the start, a trap in the entrance, a corner-to-corner run, and an XML with Windows line endings and padded numbers.
      • 
          
    • The build was reproduced with TypeScript 4.9.5 and the Dockerfile's compiler settings, and it also passes --strict. The Docker image itself was not run on the development machine.

    Build and run
    
        
    The scoring build uses the challenge's Dockerfile. It unpacks src.zip and test.zip, compiles the sources with TypeScript 4.9.5 and runs the example maze of the chosen level. Put the Dockerfile, test.zip and src.zip in one folder, then:
    
        
    docker build --tag dt_maze_challenge .
docker run --rm -it dt_maze_challenge 3 visualize
    
        
    The first argument is the level (1–3). With visualize the engine redraws the maze after every action; without it, it prints only the final result.
    
        
    To run the solver directly, without Docker:
    
        
    npm install
npx -p typescript@4.9.5 tsc
node dist/solution.js "$(cat test/example_maze_3.txt)"
    
        
    src.zip is the submission. It must contain the folder src/ with the four .ts files and nothing else. The build files (Dockerfile, test.zip, tsconfig.json, package.json) are the challenge's own and stay unchanged.

    Design notes
    
        
      
          
    • What is optimised. The solver minimises the number of actions. When two answers are equally short, it doesn't prefer either by distance or by time.
      • 
          
    • Conservative moves. It never crosses a wall, never jumps over a trap, and never walks along the outer wall. A legal answer stays legal even if the engine's left/up path check is ever fixed.
      • 
          
    • Many traps. The first 20 traps can be triggered. Any further traps are simply avoided like walls, which keeps the state small. The example mazes have at most three.
      • 
          
    • Never silent. If no way out exists, the program prints an empty <Actions>, which the engine reports as "trapped" instead of crashing.
      • 
        
    
        
    What changed from the first version
    
        
      
          
    • Level 3 was not supported at all. The program returned an empty answer.
      • 
          
    • Level 2: a step into a trap could be merged with the next step in the same direction, producing a step that went too far. Cells marked as visited before a trap reset also stayed blocked afterwards.
      • 
          
    • Steps longer than 14 cells were not split, which the engine rejects.
      • 
          
    • The search counted cells instead of actions, so its answers were often longer than necessary: 21 actions on the level 2 example instead of 17.
      • 
          
    • The parser only worked with one XML tag per line.
